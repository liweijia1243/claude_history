# Plans 页面管理方式重构设计

## 背景

当前 Plans 页面使用顶部横向 tab 展示所有 plan 文件。随着 `~/.claude/plans/*.md` 数量增加，这种方式会带来三个核心问题：

1. plan 数量多时需要频繁横向滚动，定位低效
2. 用户难以快速理解每个 plan 的主题与差异
3. 缺少搜索、筛选、排序等管理能力，无法把 Plans 当作文档列表来使用

同时，现有数据源中并不存在稳定的 `plan -> project` 关联信息。后端 `/api/plans` 仅返回 `name`、`filename`、`size`、`modified` 等文件级元数据，不能可靠地按项目组织 Plans。因此，这次重构不应建立在“按项目归档”这一假设上，而应把 Plans 视为独立文档集合进行管理。

## 目标

将 Plans 页面从“横向 tab 切换器”重构为“文档管理视图”，优先解决查找、浏览、筛选效率问题。

本次重构目标：

- 去掉不适合大量文档的横向 tab 管理方式
- 提供轻量搜索能力，覆盖标题、文件名、摘要
- 提供排序与时间范围筛选
- 让用户可以在不离开当前页面的情况下快速浏览多个 plan
- 保留现有 Markdown 渲染体验
- 不要求用户迁移已有 plan 数据

## 非目标

以下内容明确不在本次范围内：

- 建立 plan 与 project 的强关联或自动归档
- 对 Markdown 正文做全文搜索
- 收藏、归档、标签系统
- 多级目录树或复杂知识库能力
- 修改 plan 文件格式或新增持久化元数据

## 设计原则

1. **先解决检索效率，再考虑复杂组织能力**
   第一版优先把“找到 plan”这件事做好，而不是引入不可靠的项目归属推断。

2. **把 Plans 视为独立文档集合**
   既然数据源没有提供稳定 project 关联，界面上就不伪造一个“按项目组织”的结构，以免误导用户。

3. **管理视图优先于标签页视图**
   文档数量增加后，列表、筛选、排序远比 tab 更可扩展。

4. **尽量复用现有能力**
   Markdown 预览与详情获取能力保持不变，避免为了第一版体验优化而扩大改动面。

## 方案概述

Plans 页面改为三栏管理式布局：

- **左侧：筛选栏**
- **中间：plan 卡片列表**
- **右侧：Markdown 预览区**

页面职责从“在一排 tab 中切换单个文档”改为“管理并浏览一组文档”。

### 布局结构

#### 左侧筛选栏

用于承载影响整个列表结果的过滤条件，始终固定可见，不参与横向滚动。

包含：

- 搜索框
- 排序方式选择
- 时间范围筛选

第一版建议提供以下选项：

- 搜索：输入后实时过滤
- 排序：最近修改、文件名、大小
- 时间范围：全部、最近 7 天、最近 30 天

#### 中间 plan 卡片列表

展示过滤后的 plan 结果集，作为主要浏览区。

每张卡片包含：

- 主标题：优先使用 Markdown 第一行 `# 标题`，若不存在则回退到文件名
- 文件名
- 修改时间
- 文件大小
- 摘要：从正文前几行提取纯文本摘要

卡片采用紧凑信息卡风格，以提高扫描效率并保留一定内容感知能力。

#### 右侧 Markdown 预览区

保留现有 Markdown 渲染逻辑，作为选中文档的详情区。

交互方式：

- 点击卡片后在右侧打开预览
- 不跳转页面
- 不进入新路由层级
- 保持当前筛选条件不丢失

## 数据来源与字段策略

### 数据源现状

当前后端接口：

- `/api/plans`：返回 plan 文件列表及基础元数据
- `/api/plans/{name}`：返回指定 plan 的 Markdown 内容

现有接口不直接提供：

- 标题
- 摘要
- 项目归属
- 正文检索结果

### 第一版字段策略

第一版优先采用“前端派生展示字段”的方式，而不是立即扩展接口。

前端在加载 plan 内容后派生以下字段：

- `displayTitle`：从 Markdown 一级标题提取，缺失时回退文件名
- `summary`：从正文中提取前几行纯文本摘要
- `searchText`：由标题、文件名、摘要拼接而成，用于轻量搜索

这样可以在不改变数据存储结构的前提下完成大部分管理能力。

### 为什么暂不优先改后端

如果第一版就让 `/api/plans` 返回完整标题与摘要，需要在后端读取和解析全部 Markdown 文件，虽然可以实现，但会扩大本次重构范围。

考虑到本次核心问题是前端管理方式不合适，第一版更适合：

- 保持接口简单
- 通过前端状态与展示重构快速改善体验
- 在后续确认性能或交互瓶颈后，再决定是否把标题/摘要预处理下沉到后端

## 搜索与筛选规则

### 搜索范围

第一版搜索仅覆盖轻量字段，不做正文全文搜索。

包含：

- Markdown `# 标题`
- 文件名
- 摘要文本

不包含：

- 完整 Markdown 正文
- 代码块内部文本
- 任意深层标题全文索引

### 搜索行为

- 搜索输入实时生效
- 对中间列表进行过滤
- 不影响右侧预览渲染逻辑
- 若当前选中项仍在过滤结果内，则保持选中
- 若当前选中项被过滤掉，则自动切换到结果第一项
- 若无匹配结果，则右侧显示空状态提示

### 排序行为

支持以下排序维度：

- 最近修改（默认）
- 文件名
- 大小

最近修改默认降序，优先让最近写过的 plan 更容易被看到。

### 时间范围筛选

第一版提供：

- 全部
- 最近 7 天
- 最近 30 天

该筛选仅根据文件修改时间判断，不引入额外业务时间语义。

## 交互规则

### 初始状态

- 页面加载后获取 plan 列表
- 默认选中第一条结果
- 默认排序为“最近修改”
- 默认时间范围为“全部”
- 搜索框默认为空

### 结果变化时的选中逻辑

当搜索或筛选条件变化后：

1. 如果当前选中的 plan 仍在结果列表中，保持不变
2. 如果当前选中的 plan 不在结果列表中，自动选中结果第一项
3. 如果结果列表为空，清空右侧预览并显示空状态

### 浏览体验要求

- 左侧筛选始终稳定，不随预览区滚动
- 中间列表可独立滚动
- 右侧预览可独立滚动
- 页面不再出现“随着 plan 数量增长而必须横向滚动才能切换”的主交互

## UI 细节建议

### 卡片信息密度

卡片应兼顾“信息足够判断”和“列表足够高密度”。建议采用：

- 第一行：标题
- 第二行：文件名
- 第三行：修改时间 + 大小
- 第四行：两到三行摘要

### 状态表达

- 当前选中卡片需有明显高亮
- hover 态需要提升可点击感
- 搜索结果为空时，列表区显示明确空状态
- 无 plan 文件时，整页显示空状态

### 响应式策略

本次设计以桌面端为主。

若窗口变窄，可退化为：

- 左侧筛选栏收窄
- 中间列表宽度压缩
- 右侧预览保持主阅读区地位

第一版不强求移动端专门适配，但布局不应依赖固定像素宽度到无法使用。

## 实现范围

### 前端改动

核心文件：

- `web/src/views/PlansView.vue`

计划在该页内新增或重组以下状态：

- plan 列表数据
- 当前选中项
- 搜索词
- 排序方式
- 时间范围
- 派生后的过滤结果
- 标题与摘要解析结果

优先在页面内部完成，不急于抽离新组件，除非重构过程中发现模板复杂度明显失控。

### 后端改动

第一版默认**不要求**新增接口。

如果实现中发现前端为了生成标题/摘要必须额外请求大量内容、导致交互明显迟缓，可作为可选优化补充：

- 为 `/api/plans` 增加 `title`
- 为 `/api/plans` 增加 `summary`

但这属于性能/体验优化开关，不是本次设计成立的前置条件。

## 验收标准

完成后应满足以下结果：

1. Plans 页面不再使用顶部横向 tab 作为主要管理方式
2. 用户可以通过标题、文件名、摘要快速定位 plan
3. 用户可以按最近修改、文件名、大小排序
4. 用户可以按最近 7 天、最近 30 天过滤结果
5. 用户在列表和预览之间切换时无需跳页
6. 现有 Markdown 渲染效果保持可用
7. 现有 plan 文件无需迁移或补录元数据
8. 在 20+ plan 的情况下，页面仍具备可接受的查找效率

## 风险与后续演进

### 风险

1. **前端派生标题/摘要可能增加请求次数**  
   如果每个 plan 都需要单独拉取正文才能生成标题与摘要，计划数量多时可能增加加载时延。

2. **标题提取规则可能遇到格式不规范的 Markdown**  
   因此必须始终保留“回退到文件名”的兜底逻辑。

3. **摘要质量依赖 Markdown 清洗规则**  
   第一版只需做到“可辅助识别”，不要求摘要高度语义化。

### 后续演进方向

如果第一版验证有效，可以继续考虑：

- 后端预处理标题与摘要，减少前端请求压力
- 增加“最近查看”或“最近修改”快捷分组
- 增加全文搜索接口
- 增加与项目的弱关联提示（仅在有高置信度时展示）

## 结论

本次 Plans 页面重构应明确放弃“继续优化横向 tab”这一方向，改为独立文档管理视图。第一版采用“三栏布局 + 轻量搜索 + 排序 + 时间筛选 + 卡片列表 + 右侧预览”的方案，能够在不依赖 project 关联、不改动数据格式的前提下，直接解决当前 Plans 页面最核心的可用性问题。
